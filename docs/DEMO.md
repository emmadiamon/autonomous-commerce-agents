# 90-second CommerceOS demo and interview rehearsal

## Setup

1. In Codespaces, choose the latest tested branch. Configure `DASHBOARD_ADMIN_PASSWORD` as a Codespaces secret (at least 12 characters); restart if changed.
2. Run `npm install` if needed, then `npm test`, `npm run typecheck`, `npm run build`, and `npm run eval`.
3. Start Postgres: `docker compose up -d db`. Start the app: `npm run dev`.
4. Open the Codespaces forwarded port **4000 Private**, visit `/dashboard`, and sign in.
5. `OPENAI_API_KEY` is needed only for the **optional, billable** live agent demo.

## Click-through

1. **Overview:** Explain KPIs for fictional orders, processing status, low stock, and pending proposals.
2. **Inventory:** Create a proposal for Cotton T-shirt `SHIRT-002`, seeded at 8. The deterministic target of 30 proposes 22.
3. **Approvals:** Approve or reject it. Refresh; the state is persistent. No actual order is sent.
4. **Activity log:** Show the actor `demo-admin`, decision and timestamp. A separate AI event appears after an agent run.
5. **AI Workspace (optional/billable):** Under Support, ask “What is the status of order 1042?” Explain the role-limited `get_order_status` tool and shipped result.
6. **Sign out:** Verify an anonymous browser cannot view the dashboard.

## Suggested narration

> “CommerceOS is an AI-assisted e-commerce operations prototype. I built a TypeScript/Node.js GraphQL backend with three specialized agents. They only have validated, read-only tools, so a model cannot send refunds or purchase inventory. In the dashboard, low stock can trigger a deterministic recommendation, but a human must approve or reject it; the decision is stored atomically with an audit record. I also added sessions and CSRF protections for the private demo, automated tests, 14 scripted evaluations, and an opt-in live evaluation runner.”

## Likely interview questions

**Why use specialized agents?** A limited tool surface and explicit routing make role permissions easier to reason about and test. The tradeoff is brittle keyword routing for ambiguous inputs.

**How are tools secured?** The server independently validates requested tool name, argument types, maximum calls and turn counts; no model write tool exists.

**Is stock replenishment generated by AI?** No. It uses a simple deterministic rule. Agents provide order, stock and fulfillment Q&A; the approval workflow is separate.

**What happens on approval?** PostgreSQL records a one-way status transition and audit event in one transaction. It does not contact suppliers or change stock.

**Do passing results mean the LLM is 100% accurate?** No. 14/14 are deterministic scripted scenarios; 3/3 are three specific live test prompts in one run.

**What is missing for production?** Verified user identities, RBAC, tenant isolation, MFA, distributed sessions/rate limits, production observability, real integration approvals, and broader model evaluations.

## PR release checklist

The work was made in stacked draft PRs `#1 → #2 → #3 → #4 → #5 → #6 → #7 → #8`. They target each previous phase. Verify every branch and merge intentionally in order, or open a clean integration PR into `main`. Preserve working branches until the final `main` deployment is verified.
